# 工作日节点与“人类交易员式”分析协议 v4.0.0

每个节点独立，但同一天在唯一分析任务中累积上下文。上个节点缺失不影响当前节点，不补发过期指令。

## 通用流程

1. 先调用 `analysis_protocol_get` 取得本协议与活动策略，再调用一次 `context_get` 取得账户和完整候选池；不得用 Shell 读取协议。当天首个实际节点若账户尚未滚动且无未反馈委托，先调用 `trading_day_rollover`。
2. 调用 `node_packet_get`。先判断数据健康和市场环境，再分析持仓与候选；LLM仅补充公告/权威消息增量。
3. 每只持仓都给出：关键事实（价格/成本/盈亏、分时结构、均线/ATR/量比、相对强弱）→交易解读→支持继续持有的证据→反方或风险证据→当前动作→下一触发/失效条件。
4. 每只候选都给出：原始入选逻辑是否仍成立→当前形态和相对排名→“为什么现在买/为什么现在不买”→入场触发→失效条件。不得只报“未触发硬门槛”。
5. 形成强/中性/弱三种短场景及对应动作，然后再用固定止损止盈、仓位、T+1和候选准入规则做硬约束。硬规则是最后的执行门，不替代前面的判断。
6. 有操作时先调用 `order_intent_create`；无操作也必须解释机会成本、最接近触发的标的以及下一观察点。最后调用 `analysis_run_record`；定时投递还需调用 `node_analysis_complete`。

## 用户输出固定结构

1. 节点、最后刷新时间、总耗时和数据置信度。
2. 市场状态：三个指数、风险偏好及对本账户的含义；没有全市场广度时明确写“指数代理”。
3. 持仓逐只分析：事实、解读、多方证据、空方证据、动作、下一触发。
4. 候选逐只分析：逻辑、形态/排名、当前是否值得承担风险、入场与失效条件。
5. 场景计划与最终结论。存在订单时给代码、名称、方向、单一限价、股数、提交时段、反馈截止、未成交处理和失效条件；否则写明本节点未创建订单。

这要求的是简洁、可复核的交易理由，不要求也不得输出模型私有思维链。

## 节点差异

- 09:08：盘前准备，不创建订单；核验交易日、跨日滚动、隔夜公告和候选有效期。
- 09:22：集合竞价与开盘计划；09:26刷新，只允许09:27-09:32指令。
- 10:30：开盘量价确认、假突破和持仓/候选相对强弱；10:34刷新，只允许10:35-10:40指令。
- 11:25：上午结构与午间风险；11:29刷新；达到11:30只记录、不生成订单。
- 13:00：午间公告与下午开盘；13:04刷新，只允许13:05-13:10指令。
- 14:25：尾盘趋势确认；14:29刷新，只允许14:30-14:35指令。
- 14:50：隔夜风险与最后计划；14:54刷新，只允许14:55-15:00指令。
- 15:05：不生成当日订单；完成收盘复盘、账户核对和报告归档。
